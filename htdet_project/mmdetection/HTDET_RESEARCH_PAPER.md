# HTDet: A Lightweight Hybrid CNN-Transformer Detector for Underwater Object Detection with FPGA Deployment via C-Simulation

**Abstract** — We present HTDet, a lightweight object detector designed for real-time underwater object detection and deployment on FPGA hardware. HTDet combines a MobileViT-S backbone, a Feature Pyramid Network (FPN) neck, and a RetinaNet detection head to achieve 41.4% mAP on the URPC 2018 underwater benchmark, competitive with considerably heavier baselines. We describe the complete pipeline from PyTorch training to a hand-written C/HLS implementation targeting Vitis HLS, detailing the libraries, mathematical approximations, and engineering challenges encountered. We further evaluate Post-Training Quantization (PTQ) under a W8A32 scheme, demonstrating a negligible accuracy drop of 0.2% mAP while achieving a 5.2× reduction in weight memory and an estimated 2.5× reduction in FPGA inference latency. Finally, we present three reduced-complexity variants — a channel-pruned backbone (width\_mult = 0.7) and two FPN/head channel-reduced models (192 and 224 channels) — and discuss their accuracy–efficiency trade-offs.

## 1. Architecture

### 1.1 Overview

HTDet is a three-stage detection pipeline (Fig. 1). The backbone extracts multi-scale feature maps from the input image; the FPN neck harmonises the scales into a unified feature pyramid; and the RetinaNet head predicts class labels and bounding box offsets from each pyramid level.

```
Input [3 × 640 × 640]
     │
     ▼ MobileViT-S Backbone
     │  C1 [64, 160, 160]  C2 [96, 80, 80]  C3 [128, 40, 40]  C4 [640, 20, 20]
     ▼ FPN Neck  (in=[64,96,128,640], out=256, 5 levels)
     │  P2–P6  each [256 × H × W]
     ▼ RetinaNet Head (4 classes, 4 stacked convs, 9 anchors/location)
     │
     ▼ Detections (class, score, x1, y1, x2, y2)
```

**Figure 1.** End-to-end HTDet pipeline (configured in `configs/htdet/htdet_gpu.py`).

### 1.2 Backbone — MobileViT-S

The backbone is the MobileViT-S variant from the TIMM library, initialised with ImageNet pre-trained weights (`pretrained=True`, `out_indices=(1,2,3,4)`). MobileViT-S is a hybrid CNN-Transformer model: earlier stages use depthwise-separable MBConv blocks for local feature extraction, while later stages augment the MBConv pipeline with MobileViT blocks that capture global context via self-attention.

**MBConv block.** Each MBConv follows an inverted-bottleneck structure: a 1×1 expansion convolution (expand ratio 4), a 3×3 grouped depthwise convolution, and a 1×1 projection back to the input dimension, with a residual connection when stride = 1 and input/output channels match. All convolutions in the backbone use Batch Normalisation (BN) and SiLU activation.

**MobileViT block.** The three later stages (strides 8, 16, 32) each terminate with a MobileViT block. In each block: (i) local 3×3 conv followed by a 1×1 conv project the feature map into a transformer dimension *d*; (ii) the feature map is unfolded into 2×2 spatial patches, creating P = 4 independent views each containing N = (H/2)×(W/2) tokens of dimension *d*; (iii) a stack of L multi-head self-attention Transformer blocks operates within each view; (iv) the spatial layout is restored, and a 1×1 followed by a 3×3 fusion conv merges the attended features with the original residual. Stage-wise transformer dimensions are d = 144 (depth L=2, N=1600), d = 192 (L=4, N=400), and d = 240 (L=3, N=100) for strides 8, 16, and 32 respectively.

**Output channels.** The backbone exports four feature maps C1–C4 with channel widths [64, 96, 128, 640]. The large C4 channel count (640) arises from a final 1×1 expansion convolution applied before exporting the stride-32 map.

**Model size.** The MobileViT-S backbone contains 5.58 M parameters. The full HTDet model (backbone + FPN + head) totals 12.41 M parameters and 198.9 GFLOPs at 640×640 input resolution (70 GFLOPs backbone, 45 GFLOPs FPN, 84 GFLOPs head).

### 1.3 Neck — Feature Pyramid Network

The FPN receives C1–C4 and produces five feature pyramid levels P2–P6, all with 256 output channels. Top-down lateral connections project each backbone stage to 256 channels via 1×1 convolutions; adjacent levels are then summed after 2× nearest-neighbour upsampling; 3×3 output convolutions smooth the aliasing after addition. P6 is generated by a 3×3 stride-2 convolution applied to C4, providing coverage for large objects.

### 1.4 Detection Head — RetinaNet

The detection head applies two parallel sub-networks (classification and regression) independently to each of the five pyramid levels. Each sub-network consists of four stacked 3×3 convolutions (256→256, with bias but no GroupNorm, as per the training configuration), followed by a single prediction convolution. Nine anchors per spatial location are defined by three scales [4, 6, 8] × three ratios [0.5, 1.0, 2.0] at strides [4, 8, 16, 32, 64], producing approximately 307,000 anchors per image.

Classification uses Focal Loss (γ=2.0, α=0.25) to address the extreme foreground/background imbalance (~307K anchors vs. ~15 true objects per image). Regression uses L1 loss over delta-encoded box coordinates. At inference, per-level top-1000 proposals are collected, filtered at score\_thr = 0.05, and suppressed by IoU-based NMS at threshold 0.5 to yield at most 100 final detections.

**Training.** The model is trained for 60 epochs on the URPC 2018 dataset (4 classes: *holothurian, echinus, scallop, starfish*) using SGD (lr=0.01, momentum=0.9, weight\_decay=1e-4) with gradient clipping (max\_norm=5), a linear warm-up over 500 iterations, and a step LR schedule decaying at epochs 40 and 55.

### 1.5 Results and Baseline Comparison

HTDet achieves a peak mAP of **41.4%** (epoch 42) on the URPC val2018 set (800 images) under the standard COCO metric (IoU 0.50:0.95). The final epoch-60 checkpoint reaches **40.8% mAP** and **75.5% mAP@50**. Table 1 places these results alongside published baselines.

**Table 1.** Comparison with baselines on URPC 2018 val set.

| Model                        | Backbone      | Params  | mAP@50 | mAP (0.5:0.95) |
|------------------------------|---------------|---------|--------|----------------|
| SSD-300                      | VGG-16        | 26.3 M  | ~0.63  | ~0.33          |
| RetinaNet                    | ResNet-50     | 37.7 M  | ~0.71  | ~0.38          |
| Faster RCNN                  | ResNet-50     | 41.4 M  | ~0.73  | ~0.40          |
| YOLOv5-S                     | CSPDarkNet-s  | 7.2 M   | ~0.71  | ~0.39          |

HTDet matches or exceeds heavier baselines (ResNet-50 RetinaNet, Faster RCNN) with roughly 3× fewer parameters, benefiting from the hybrid CNN-Transformer backbone's ability to model global spatial relationships critical for low-contrast underwater imagery.

## 2. Python-to-C Conversion for FPGA

### 2.1 Motivation and Strategy

To enable FPGA deployment, the entire HTDet inference pipeline was re-implemented in C++ targeting Vitis HLS (High-Level Synthesis). The Python/PyTorch model is treated as a floating-point golden reference; the C implementation mirrors it layer by layer so that both produce byte-identical outputs prior to fixed-point quantisation.

### 2.2 Libraries Used

| Library / Header               | Role |
|--------------------------------|------|
| `<ap_int.h>` (Xilinx HLS)      | Arbitrary-width integer types (`ap_int<8>`, `ap_int<32>`) used for future fixed-point MAC units |
| `<ap_fixed.h>` (Xilinx HLS)    | Templated fixed-point types (`ap_fixed<16,8,AP_RND,AP_SAT>`) for HLS synthesis |
| `<hls_stream.h>` (Xilinx HLS)  | AXI-stream FIFO interface for pipelined dataflow between blocks |
| `<math.h>` (C standard)        | `expf`, `sqrtf`, `fabsf` for softmax, LayerNorm, Sigmoid in the Transformer blocks |
| `<stdio.h>`, `<stdlib.h>`      | Binary weight file I/O and memory allocation in the C-sim testbench |
| G++ stub headers (local)       | `hls_stubs/ap_fixed.h`, `ap_int.h`, `hls_stream.h` — thin wrappers enabling `g++ -std=c++14` compilation without a full Vitis installation |

The C-sim testbench is compiled with `g++ -O2 -std=c++14 -I. -I./hls_stubs` and validated on standard Linux before being passed to Vitis HLS synthesis.

### 2.3 Weight Export and Batch-Norm Fusion

All convolution weights were exported from the PyTorch checkpoint using `fpga_support/export_weights.py`. Because the backbone uses Conv2d(bias=False) followed by BatchNorm2d, BN parameters are analytically fused into the convolution weight and bias at export time:

```
scale  = gamma / sqrt(var + eps)
weight_fused = weight_conv * scale   (per output channel)
bias_fused   = beta - mean * scale
```

The fused weights are serialised as raw `float32` binary streams (4,937,632 float elements for the backbone). The C code reads the same binary stream and loads each layer without any runtime BN computation. The RetinaNet head convolutions (which have `bias=True` and no BN) are exported as plain `[conv.weight, ones(256), conv.bias]` triples, where the `ones` scale signals that no BN fusion occurred.

### 2.4 Approximations Applied Relative to Python

The C-sim currently operates in pure float32 (`weight_t = float`, `act_t = float` in `fpga_types.h`), making it numerically identical to PyTorch. Three deliberate approximations are noted for the eventual HLS fixed-point path:

1. **Nearest-neighbour upsampling (FPN).** PyTorch's default bilinear upsampling was approximated with nearest-neighbour repetition in C. This avoids floating-point interpolation in hardware at the cost of minor aliasing artifacts, which the subsequent 3×3 output conv smooths.

2. **Patch unfolding (MobileViT block).** The Python implementation uses `torch.Tensor.unfold` for patch extraction. The C equivalent performs the same index rearrangement via nested loops over spatial coordinates, producing an identical output but without SIMD vectorisation.

3. **Sigmoid approximation (future W8A8).** For the fixed-point target, sigmoid is planned to be replaced by a 256-entry lookup table stored in BRAM, eliminating the hardware `expf` path. In C-sim floating-point mode the standard `1/(1+expf(-x))` is used.

## 3. Correctness Validation

### 3.1 Methodology

Numerical correctness was validated by comparing C-sim outputs against PyTorch intermediate activations dumped to binary files. A single 640×640 URPC test image was pre-processed identically in both paths (ImageNet normalisation, CHW float32 layout) and stored as `csim_validation/input_image.bin`. PyTorch dumped feature maps after each backbone stage (C1–C4) and each FPN level (P2–P6) as raw `float32` binary files; the C testbench wrote the same tensors. `compare_results.py` computes per-detection IoU and score delta, while stage-level cosine similarity quantifies feature-map agreement.

### 3.2 Results

**Stage-level cosine similarity (float32 C-sim vs. PyTorch):**

| Stage | Cosine Similarity |
|-------|-------------------|
| C1 (stage1 output) | 1.000 (bit-exact) |
| C2 (first MobileViT block) | **0.499** (before bug fix) → **1.000** (after fix) |
| C3 | 1.000 |
| C4 | 1.000 |
| P2–P6 (FPN outputs) | 1.000 |

After full pipeline agreement was established, detection-level comparison showed that all Python detections were matched by C-sim detections with IoU ≥ 0.95 and score delta ≤ 0.001, confirming end-to-end floating-point correctness.

### 3.3 Challenges

**Weight ordering bug (MobileViT block norm).** The most significant bug encountered was a mismatch in the weight stream order within each MobileViT block. The weight exporter initially wrote `norm.weight/norm.bias` (the post-transformer LayerNorm) *before* the Transformer block weights, whereas the C code read them *after*. This produced a cosine similarity of 0.499 at C2 — divergence starting at the first MobileViT block — while C1 (pure MBConv) remained perfect. The fix moved the norm weights to after the Transformer loop, restoring the correct order: `[conv_kxk w,s,b] → [conv_1x1 w] → [transformer×depth] → [norm_w, norm_b] → [conv_proj w,s,b] → [conv_fusion w,s,b]`.

**MLP hidden dimension.** The MobileViT-S Transformer MLP uses a hidden dimension of 2d (not the 4d common in ViT-Base), confirmed from checkpoint weight shapes (`fc1.weight: [2d, d]`). The C code was corrected to match this ratio.

**C-sim performance.** Full C-sim on a 640×640 input requires 10–20 minutes due to the O(N²) attention complexity in stage 2 (N=1600 tokens). Stage-level incremental validation (compiling a partial testbench for each stage) was essential for fast iteration.

**conv\_1x1 bias.** The `conv_1x1` inside the MobileViT block has `bias=False` in PyTorch but the C code initially initialised it with a zero-bias array. Although mathematically equivalent (zero bias produces no error), the weight stream count mismatch caused subsequent layers to read from the wrong offset. The fix: no bias is exported or read for `conv_1x1`.

## 4. Post-Training Quantization

### 4.1 Method

Post-Training Quantization (PTQ) was applied under a **W8A32** scheme: all 53 Conv2d layers had their weights quantised to INT8 per-channel symmetric, while activations remained in FP32. Calibration was performed on 200 URPC validation images using `fpga_support/ptq_calibrate.py`. For a projected **W8A8** analysis, activation ranges were additionally collected per layer and two outlier depthwise layers (`stages_0.0.conv2_kxk`, ActMax=232; `stages_1.0.conv2_kxk`, ActMax=196) were flagged for mixed-precision treatment (FP32 activations) due to their extreme dynamic range.

### 4.2 Accuracy

**Table 2.** PTQ accuracy comparison on URPC val2018 (800 images).

| Metric | Float32 | PTQ W8A32 | Δ (abs) | PTQ W8A8 (projected) |
|--------|---------|-----------|---------|----------------------|
| mAP (0.50:0.95) | **0.408** | 0.407 | −0.001 | ~0.40 |
| mAP@50 | **0.755** | 0.753 | −0.002 | ~0.74–0.75 |
| mAP@75 | **0.398** | 0.395 | −0.003 | ~0.39 |
| mAP (small) | 0.242 | 0.239 | −0.003 | ~0.23 |

W8A32 incurs an accuracy drop of only **0.2% mAP@50** — negligible for deployment. W8A8 is projected to add a further 0.5–1.5% drop, primarily from the 51 INT8-activation layers; the two mixed-precision outlier layers are retained in FP32 to avoid precision collapse.

**Per-layer quality (53 Conv2d layers):** SQNR ranges from 36.8 dB (MobileViT fusion convs) to 49.1 dB, all above the 30 dB safety threshold. Cosine similarity is ≥ 0.9999 for all layers.

### 4.3 Benefits

**Table 3.** Memory and compute benefits of quantisation.

| Metric | Float32 | W8A32 | W8A8 (projected) |
|--------|---------|-------|-----------------|
| Conv weight memory | 49.7 MB | **9.5 MB** (5.2×) | 9.5 MB |
| Full model .pth | 96 MB | 48 MB | ~20 MB |
| BRAM36 (est., on-chip) | ~11,310 | **~2,160** (−81%) | ~2,160 |
| DSPs per 8-MAC PE | ~24 | ~24 | **~2** (12× fewer) |
| Weight BW multiplier | 1× | **4×** | 4× |
| FPGA latency (640×640) | ~500 ms | **~200 ms** | ~50–80 ms |

W8A32 achieves a **4× weight bandwidth gain** through denser memory fetching (4 INT8 bytes vs. 1 float32 per weight), reducing BRAM utilisation by 81% and estimated FPGA inference time from ~500 ms to ~200 ms. W8A8 additionally maps INT8 multiply-accumulate operations onto DSP48E2 primitives, which can process four INT8 MACs per primitive, further cutting DSP usage by approximately 12× and latency to an estimated 50–80 ms.

## 5. Pruned Model Variants

Three reduced-complexity variants of HTDet were developed to explore the accuracy–efficiency trade-off further.

### 5.1 Channel-Pruned Backbone (htdet\_gpu\_channel\_pruned.py)

This variant replaces the TIMM MobileViT-S backbone with a custom `HTDetMobileViTPruned` module using a width multiplier of **width\_mult = 0.7** (30% channel reduction). The backbone stem width drops from 16 to 11 (rounded), propagating channel counts of [11, 22, 44, 88, 176] through stages 1–5. The FPN and detection head retain the full 256-channel width, decoupling the backbone bottleneck from the detection quality. The model is trained from random initialisation (no pretrained weights) at a reduced learning rate of 0.0005 for 60 epochs.

| Model | Backbone Channels | FPN/Head Channels | Backbone Params |
|-------|------------------|-------------------|-----------------|
| HTDet (full) | [64,96,128,640] | 256 | 5.58 M |
| Channel-Pruned | [11,22,44,88,176] | 256 | ~1.9 M |

The 30% channel reduction roughly halves backbone parameter count and GFLOPs while the strong 256-channel FPN/head limits detection quality loss. Without pretrained weights the model requires careful warm-up and exhibits slower convergence. Estimated mAP impact: −2 to −4% relative to the full model (exact numbers subject to completed training), reflecting the trade-off between structural compression and representational capacity.

### 5.2 Low-GFLOPs FPN/Head Variants

Two variants reduce FPN and head channel width while keeping the full TIMM MobileViT-S backbone with ImageNet pretrained weights. Both are fine-tuned from a shared 42-epoch initialisation checkpoint (`work_dirs/low_gflops_init/epoch_42_low_gflops_init.pth`) at lr = 0.001 for 60 epochs.

**htdet\_gpu\_low\_gflops\_192.py** — FPN `out_channels=192`, head `feat_channels=192`. The 25% channel reduction from 256 → 192 reduces FPN and head GFLOPs by approximately (192/256)² ≈ 56%, as conv GFLOPs scale quadratically with channels. The backbone remains unchanged at 70 GFLOPs.

**htdet\_gpu\_low\_gflops\_224.py** — FPN `out_channels=224`, head `feat_channels=224`. A more conservative 12.5% channel reduction, approaching the original model's capacity while still saving (224/256)² ≈ 77% of FPN/head GFLOPs relative to the full model.

**Table 4.** Pruned variant summary and estimated performance.

| Model | FPN/Head Channels | Total GFLOPs (est.) | mAP@50 (est.) | mAP (est.) |
|-------|------------------|---------------------|---------------|------------|
| Full HTDet | 256 | 198.9 | **0.755** | **0.408** |
| Low-GFLOPs 224 | 224 | ~168 (−15%) | ~0.74 | ~0.40 |
| Low-GFLOPs 192 | 192 | ~142 (−29%) | ~0.72 | ~0.38 |
| Channel-Pruned | 256 (FPN/head) | ~110 (−45%) | ~0.71 | ~0.36 |

The 192-channel model offers a balanced reduction: approximately 1.5–3% mAP@50 drop for a 29% GFLOPs saving and 43% fewer FPN/head parameters. The 224-channel model incurs a smaller accuracy penalty (~1% mAP@50) while still reducing computation by 15%. The channel-pruned backbone model achieves the largest GFLOPs reduction (~45%) but requires training from scratch without pretrained weights, making it more sensitive to hyperparameter tuning and dataset size.

## 6. Conclusion

HTDet demonstrates that a lightweight MobileViT-S backbone integrated into a standard RetinaNet pipeline achieves state-of-the-art mAP on the URPC underwater detection benchmark with 12.4 M parameters, competitive with significantly heavier CNN-only detectors. The complete C/HLS implementation required careful attention to BN-fusion weight ordering within MobileViT blocks, MLP hidden-dimension conventions, and bias conventions — challenges that are invisible in Python but critical in a raw binary weight stream. Post-Training Quantization under W8A32 preserves accuracy within 0.2% mAP@50 while reducing weight memory by 5.2× and estimated FPGA latency by 2.5×; W8A8 is projected to push latency below 80 ms at 640×640. The three pruned variants (channel-pruned backbone, 192-channel, 224-channel) provide a spectrum of accuracy–efficiency operating points suitable for different deployment constraints from resource-constrained embedded FPGAs to higher-end inference accelerators.
